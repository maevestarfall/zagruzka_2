# Changelog — 🖥 render.com (деплой на сервер из «Публикации»)

Новая кнопка **🖥 render.com** в Master Room (главное меню) + авто-деплой
после публикации репозитория на GitHub. GitHub-публикация (zip → репо →
отчёт со ссылкой) **не тронута** — render идёт поверх неё.

## v17.26 — аудит + честные исправления

Разобрали «что работает / что симуляция» и поправили:

1. **Сессия (storage_state) теперь работает на Camoufox** (приоритетный движок) —
   раньше cookies загружались/сохранялись только на Cloak/Playwright, а на
   Camoufox (и nodriver) — нет. Теперь Camoufox открывает явный контекст:
   импорт cookie и «вход держится между запусками» работают на основном движке.
   На nodriver формат Playwright не поддерживается — добавлено честное
   предупреждение в лог (без фейковой поддержки).
2. **Честный успех деплоя.** Раньше `ok` = «движок не упал» (клик мог
   промахнуться без ошибки → ложный ✅). Теперь в конце макроса читается текст
   страницы и проверяется: не застряли ли на странице входа и виден ли экран
   сервиса. Отчёт различает: ✅ подтверждено / 🟡 не подтверждено /
   ⚠️ ошибка («не залогинен», «вёрстка изменилась»).
3. **Убраны пустышки** (хранились, но на поведение не влияли):
   🔬 Analyzer PRO, 📤 Способ публикации (обе ветки гнали один и тот же макрос),
   🐙 PAT-токен GitHub (в деплое не использовался; вход теперь через «Способ входа»).
4. **📖 Инструкция** — новая кнопка в меню render: пошагово что делать и что из
   этого выйдет (1. репо на GitHub → 2. токен бота → 3. способ входа →
   4. прочие → 5. авто-загрузка → 6. загрузить сейчас + расшифровка отчёта).

## v17.26 — 🔐 Способ входа (login method)

Добавлено меню **«🔐 Способ входа»** на экране `mr:render` с тремя кнопками
(как и просили — все три способа видны сразу):

1. **GitHub OAuth** — ✅ **реализовано**. Бот заходит на render.com, жмёт
   «Continue with GitHub», и если в сохранённой сессии браузера GitHub ещё
   разлогинен — заполняет форму логина GitHub (👤 логин + 🔑 пароль из меню)
   и один раз подтверждает доступ Render. Сессия сохраняется в
   `render_session.json`, поэтому дальше вход держится сам. Шаги best-effort:
   если сессия уже есть — клики входа просто ничего не делают и деплой идёт
   дальше. Прогресс-бар в TG теперь включает фазу входа («🔐 Вхожу на render»).
2. **Email + пароль** — ✅ **реализовано**. В подменю задаёшь 📧 email и
   🔑 пароль render. Бот открывает страницу входа render, заполняет форму и
   жмёт «Sign in». Сессия сохраняется в `render_session.json`.
3. **Импорт cookie/сессии** — ✅ **реализовано**. Кнопка «⬆️ Загрузить
   storage_state.json»: присылаешь JSON-файл сессии (Playwright storage_state,
   cookies + localStorage), бот пишет его как сессию render
   (`render_session.json`) — деплой заходит уже залогиненным, без логина.
   Есть «🗑 Удалить сессию» и индикатор статуса.

Технически: `state.py` — `get/set_render_login_method`, `get/set_render_gh_login`,
`get/set_render_gh_password`, `get/set_render_email`, `get/set_render_password`;
`render_deploy.py` — `build_github_login_steps()` + `build_email_login_steps()`
+ Phase 0 в `deploy_to_render(login_method=, gh_login=, gh_password=, email=,
password=)` (метод `cookie` — без шагов, просто используется сохранённая сессия);
`handlers.py` — подменю `mr:render:login*` (github / email / cookie) и проброс
параметров в деплой.

## Что добавлено

### Экран 🖥 render.com (`mr:render`)
- **🤖 Токен бота** — значение, которое бот впишет в env-переменную
  `BOT_TOKEN` на render.com (то самое «123»). Сохраняется и подставляется
  при каждом деплое; можно менять и удалять.
- **🐙 Токен GitHub** — для входа на render.com через GitHub.
- **🔁 Авто-загрузка вкл/выкл** — после успешного пуша на GitHub бот сразу
  деплоит на render.
- **🚀 Загрузить на render сейчас** — ручной запуск для последнего
  опубликованного репозитория.
- **« Вернуться**.

### Деплой через stealth-браузер (`render_deploy.py`)
Всё идёт через существующий `workers.browser_clicker.run_browser_macro`
(человеческий курсор, фингерпринт, прокси — без изменений), в две фазы:

**Фаза 1 — Suspend старого сервиса** (пропускается на самом первом деплое):
открыть dashboard → войти в группу «All services are up and running» →
открыть старый сервис (например `zagruzka_6`) → ⋮ → «Suspend» → вписать
красную фразу `sudo suspend web service zagruzka_6` → «Suspend Web Service».

**Фаза 2 — Создать новый Web Service**: dashboard → «Create new project» →
имя проекта (= имя репо, напр. `zagruzka_7`) → «Create new service» → «New
Web Service» → выбрать репо `owner/zagruzka_7` → тариф **Free** (512 МБ /
0.1 CPU) → Environment Variables: `BOT_TOKEN` = <твоё значение> →
«Advanced» → Health Check Path `/healthz` → «Deploy web service».

Имя старого сервиса для Suspend берётся из `render_last_project` (имя
предыдущего задеплоенного репо), новое — из только что опубликованного.
Скриншоты обеих фаз присылаются в чат для визуальной проверки.

## Важно (ограничения)
- render.com — React-SPA: макрос кликает по **видимому тексту** кнопок
  («Create new project», «New Web Service», «Free», «Advanced», «Deploy web
  service», «Suspend» …). Если render поменяет формулировки/верстку — может
  понадобиться правка текста шагов в `render_deploy.py`.
- ⋮ (три точки) и поля env/имя проекта подбираются эвристически
  (placeholder/aria) — это самые хрупкие шаги.
- **Вход на render.com**: stealth-браузер каждый запуск стартует с чистой
  сессии (куки не персистятся). Для стабильного входа через GitHub нужна
  сохранённая сессия — это отдельная доработка движка (по запросу).

Выбор (радио, ✅/⚪️), сохраняется:
- **Обычная** — как сделано сейчас.
- **Браузерная (стелс)** — через stealth-браузер.

> Сейчас оба варианта ведут деплой через один stealth-движок; выбор
> сохраняется и показывается в отчёте. Точка ветвления готова — если нужно

### 🧩 Прочие (`mr:render:misc`) — динамические вкл/выкл
- **🗑 Удалять предыдущий проект** — старый сервис удаляется (Settings →
  Delete Web Service → подтверждение именем). Имеет приоритет над паузой.
- **💤 Паузить предыдущий проект** — Suspend старого сервиса (прежнее
  поведение; по умолчанию вкл).
- **🔬 Analyzer PRO (поиск функций)** — флаг передаётся в деплой и
  отражается в отчёте (хук под поиск функций/элементов).

Все тумблеры — динамические: текст кнопки сразу показывает вкл ✅ / выкл ⛔.
Логика очистки старого проекта: если «удалять» вкл → удаление; иначе если
«паузить» вкл → Suspend; иначе ничего.

## Обновление: прогресс-бар деплоя + сохранение сессии браузера

### Живой прогресс в TG (как при заливке репо)
Во время деплоя на render сообщение в чате обновляется баром:
`🖥 render.com (браузерная) · 💤 Гашу старый… ████░░░░░░ 40% · шаг 5/37`,
затем `🚀 Создаю новый…` до 100%. Единый счётчик через обе фазы.
Реализовано через новый необязательный `progress_cb` в `run_browser_macro`
(вызывается перед каждым шагом) и сквозной счётчик в `deploy_to_render`.

### Сохранение сессии браузера (`storage_state`)
`run_browser_macro` получил необязательный `session_state_path`: для
Playwright-движков сессия (cookies + localStorage) сохраняется после запуска
и подгружается на следующем — то есть **вход на render держится между
запусками**. Стелс не затронут (только дозагрузка cookies в контекст).
Render-деплой использует общий файл `session/render_session.json`.

### ⚠️ Аудит входа на render (честно)
Сейчас в макросе **нет шага логина**, а свежий браузер стартует
разлогиненным → на чистой машине render.com покажет страницу входа, и клики
не найдут целей. GitHub-**токен** для браузерного входа не подходит
(PAT ≠ веб-сессия; OAuth/2FA не автоматизируются токеном).

`storage_state` решает это, НО сессию нужно сначала один раз создать. Нужен
выбор способа логина (по нему доделаю рабочий вход):
  1. **render email+password** — Render это поддерживает, автоматизируется
     надёжно (добавлю поля и шаги логина).
  2. **Импорт cookie/`storage_state`** — вставляешь сохранённую сессию один
     раз, дальше переиспользуется.
  3. **GitHub OAuth** — самый хрупкий (2FA ломает автоматизацию).
