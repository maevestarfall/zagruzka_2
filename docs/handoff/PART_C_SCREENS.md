# Часть C — Покрытие экранов волн 2-3 (этап 4 ТЗ)

## Цель

Сейчас на сайте и (после частей A/B) в Discord/VK полноценно работают
только экраны `main` и `settings` — остальные кнопки отвечают
«доступно только в Telegram» (409 tg_only). Задача: перенести в
нейтральный формат read-only и простые информационные экраны, чтобы
максимум меню работал на всех платформах.

## Файлы (создать, ничего больше не трогать)

- `bot/gateway/screens_wave2.py` — все новые экраны и действия
- `tests/test_gateway_wave2.py` — тесты

Существующие `bot/gateway/screens.py`, `bot/wizard.py` и обработчики
аддонов НЕ менять. Данные для экранов брать из тех же модулей, что
использует `bot/wizard.py` (импортировать `bot.storage`, аддоны и т.д.
и читать их публичные функции — только чтение).

## Волна 2 (обязательная): информационные экраны

Зарегистрировать через `register_screen` нейтральные версии:

| screen_id | Источник в TG (callback) | Содержимое |
|-----------|--------------------------|------------|
| `tokens` | `main:tokens` | статистика токенов текстом |
| `debates` | `main:debates` | описание фичи + список тем (docs/DEBATE_TOPICS) |
| `promptbox` | `main:promptbox` | список сохранённых промтов (read-only) |
| `github` | `main:github` | список подключённых репозиториев (read-only) |
| `projmap` | `main:projmap` | сводка карты проекта текстом |
| `misc` | `misc:home` | список прочих функций со статусами |

Правила:
- `parent` каждого экрана — `"main"` (или логичный родитель).
- Тексты и порядок кнопок — 1:1 с TG-версией, где это возможно.
- Кнопки, ведущие в интерактивные диалоги (FSM, загрузка файлов),
  НЕ регистрировать как действия — оставить их action как в TG:
  dispatch сам ответит tg_only с deep-link. То есть кнопку показываем,
  но её «глубина» пока остаётся в Telegram.
- Гейтинг: поля `owner_only` у MenuScreen НЕТ — доступ проверяется
  внутри builder-функции. Для админских экранов (`tokens`, `projmap`,
  `misc`, `github`): если `not access.can_admin(user_id)` — вернуть
  экран с текстом «Доступно только владельцу» без кнопок (кроме
  «Назад»). Образец — `build_settings_screen` в
  `bot/gateway/screens.py`: гостевые кнопки он фильтрует через
  `bot.feature_gate.filter_menu_rows` (наши MenuButton уже совместимы
  с ним через свойство `callback_data`).

## Волна 3 (если останется время): простые действия

Через `register_action` перенести действия-переключатели без диалогов:
- вкл/выкл фич из `misc:home` (тумблеры)
- очистка «мусора» (`main:dump` — только само действие подтверждения)
Каждое действие: проверить, что аналогичный обработчик в
`bot/wizard.py` — простой (одна операция + перерисовка экрана), и
воспроизвести ту же операцию через публичные функции storage/аддона.
Если обработчик сложный (FSM, вопросы) — пропустить, оставить tg_only.

## Главное правило эквивалентности (A2 из ТЗ)

Тот же пользователь на любом экране видит те же кнопки, что и в TG:
- владелец — всё;
- гость — только то, что разрешено feature_gate.
Для гостевой видимости использовать те же функции, что settings-экран
этапа 1 (см. `build_settings_screen` в `bot/gateway/screens.py` как
образец: чтение `bot.access` / `bot.feature_gate` только на чтение).

## Тесты (минимум)

1. Каждый новый экран строится для владельца и для гостя без исключений.
2. Все action всех новых экранов ≤ 64 байта UTF-8.
3. У каждого экрана корректный `parent` (существующий screen_id).
4. Гость не видит owner-only экраны (`build_screen(...)` → None или
   пустой доступ — как в этапе 1).
5. Перенесённые действия волны 3: гость → forbidden, владелец → работает
   (с подменённым storage).

## Критерии приёмки (из ТЗ)

- A8: большинство пунктов меню открываются на сайте без «только в Telegram».
- A2: набор кнопок на всех платформах идентичен TG для того же пользователя.
