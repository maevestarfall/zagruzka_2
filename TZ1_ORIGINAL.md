## 0. TL;DR для исполнителя (прочитай это, даже если больше ничего не прочтёшь)

1. В меню **⚙️ Настройки** появляется кнопка **«🌐 Платформы: TG · Site · Discord · VK»**.
2. Ботом можно управлять с четырёх поверхностей: **Telegram** (как сейчас), **сайт** (расширение существующей панели VISION), **Discord**, **VK**.
3. Меню описывается **один раз** в нейтральном формате `MenuScreen`; каждая платформа лишь рендерит его в свой нативный вид. Отсюда автоматически выполняется главное требование владельца: **«добавил кнопку — она видна на всех площадках»**.
4. Подключение Discord/VK — **кнопками изнутри Telegram** (паттерн Slack-коннектора: прислал токен → бот проверил → сообщение с токеном удалено → токен в `state.json` под маской). Никаких новых обязательных env vars.
5. Права: владелец привязывает свои Discord/VK-аккаунты **одноразовым кодом**. Все остальные на чужих платформах — гости, прогоняются через существующий `feature_gate`.
6. Работа ведётся **пятью этапами**, каждый деплоится и работает отдельно. Перед кодом — обязательный research-этап (§9) с фиксацией выводов в `AI_CHANGELOG.md`.

## 1. Постановка задачи

### 1.1. Формулировка владельца (дословно)

> «Сделать кнопку в настройках "tg site discord vk". Я хочу, чтобы в ней функционале была полная интеграция через сайт (кнопка VISION), либо Discord, либо VK — управлять этим проектом. Сейчас я могу только управлять через ТГ, но я хочу, чтобы проект мог жить на разных платформах и управляться разными платформами. Если дополняется какая-то кнопка — то она видна на всех площадках.»

### 1.2а. Формализация требований в нотации EARS

Каждая формулировка — атомарная и проверяемая одним тестом. При расхождении трактовок §1.2 и §1.2а — приоритет у §1.2а.

| ID | EARS-формулировка |
|---|---|
| R1-E | КОГДА владелец открывает меню «⚙️ Настройки», СИСТЕМА ДОЛЖНА показать кнопку «🌐 Платформы»; ЕСЛИ пользователь — гость, СИСТЕМА ДОЛЖНА скрыть эту кнопку |

## 3. Архитектура: Платформенный шлюз

### 3.1. Принцип

**Одно меню — много рендереров.** Сегодня меню «прибито» к aiogram (`InlineKeyboardMarkup`). Вводим нейтральный промежуточный формат, и каждая платформа получает свой тонкий адаптер:

```
                         ┌─────────────────────────────┐
                         │   MenuScreen (нейтральный) │
                         │   + dispatch_action()      │
                         └─────────────┬──────────────┘
           ┌───────────────┬───────────┼───────────────┬───────────────┐
           ▼               ▼           ▼               ▼               │
   adapters/telegram  adapters/web  adapters/discord  adapters/vk      │
   (aiogram, как      (JSON для     (discord.py:      (vkbottle:       │
    сейчас, 1:1)       VISION SPA)   Buttons/Select)   inline keyboard)│
           │               │           │               │               │
           ▼               ▼           ▼               ▼               ▼
       Telegram         Сайт        Discord           VK        будущие платформы
```

### 3.2. Структура нового пакета

```
bot/gateway/
  __init__.py        # мягкая регистрация (try/except), фабрика адаптеров
  menu.py            # MenuScreen / MenuButton / рендер-контракты
  dispatch.py        # dispatch_action() — единая маршрутизация действий
  identity.py        # привязка внешних аккаунтов, одноразовые коды, роли
  broadcast.py       # рассылка уведомлений владельцу по платформам (этап 5)
  media_bus.py       # медиашина: реестр артефактов, кросс-платформенный вход/выход медиа (§6А)
  wizard_ui.py       # экраны gateway:* внутри TG (кнопка, подменю, FSM токенов)
  adapters/
    __init__.py
    base.py          # ABC: render(screen), send(text), edit(...), start(), stop(), health()
    telegram.py      # референс-адаптер (обёртка текущего поведения)
    web.py           # мост в Fable5/VISION
    discord.py       # discord.py ≥ 2.x, Gateway (WebSocket)
    vk.py            # vkbottle, Bots Long Poll
```

### 3.3. Контракт данных: `MenuScreen`

```python
# bot/gateway/menu.py
from dataclasses import dataclass, field

@dataclass(frozen=True)
class MenuButton:
    text: str                  # "🎭 Роли" — с эмодзи, как в TG
    action: str                # ТА ЖЕ callback-строка, что сейчас: "roles:menu"
    url: str | None = None     # для URL-кнопок (VISION, инструкции)

@dataclass(frozen=True)
class MenuScreen:
    screen_id: str             # "settings", "gateway:home", ...
    title: str                 # "⚙️ Настройки"
    body: str = ""             # текст над кнопками (markdown-safe)
    rows: list[list[MenuButton]] = field(default_factory=list)
    parent: str | None = None  # для кнопки «↩️ Назад» на платформах без своей истории
```

Правила:

- `action` — существующие `callback_data`-строки. Ничего не переименовывать: на них завязан `feature_gate.FEATURE_CALLBACK_PREFIXES`.
- `MenuScreen` строится **на момент запроса** (в TG и так каждый показ — свежий рендер). Поэтому push-синхронизация меню между платформами НЕ нужна: устаревших копий не существует по построению.
- Рефакторинг `_kb_*`-функций: каждая начинает строить `MenuScreen`, а для TG остаётся тонкая функция-конвертер `screen_to_tg(screen, user_id) -> InlineKeyboardMarkup`. Пиксель-в-пиксель идентичный вывод в TG проверяется тестом (§10).
- Гейтинг: `filter_menu_rows()` применяется к `MenuScreen.rows` ДО передачи адаптеру — один раз, в одном месте (`dispatch.py`), а не в каждом адаптере.

### 3.4. Контракт действий: `dispatch_action`

```python
# bot/gateway/dispatch.py
@dataclass
class GatewayContext:
    platform: str              # "telegram" | "web" | "discord" | "vk"
    external_id: str           # id пользователя на платформе
    user_id: int | None        # смапленный TG user_id (None = не привязан → гость)
    reply: Callable            # как ответить на этой платформе

@dataclass
class ScreenResult:
    screen: MenuScreen | None = None   # новый экран (перерисовать сообщение)
    text: str | None = None            # или просто текст
    error: str | None = None           # человекочитаемая ошибка

async def dispatch_action(action: str, ctx: GatewayContext) -> ScreenResult: ...
```

Ключевые решения:

- **Реестр, а не переписывание.** Вводится `SCREEN_REGISTRY: dict[str, ScreenBuilder]` — экраны регистрируются по мере покрытия (§7). Действие, которого нет в реестре, на не-TG платформе получает вежливую заглушку:
  > «⏳ Этот экран пока доступен только в Telegram» + deep-link `https://t.me/<bot>?start=...`
- В Telegram НИЧЕГО не меняется: aiogram-роутеры работают как раньше; `dispatch_action` для TG — опциональный путь, включаемый по мере миграции экранов.
- Каждое действие проходит через гейт: guest без права `use` на фичу получает тот же отказ, что в TG (middleware-логика из `feature_gate` переиспользуется, см. `build_feature_use_gate_middleware`).

## 4. UX-спецификация (Telegram — эталон, остальные платформы повторяют смысл)

### 4.1. Кнопка в ⚙️ Настройках (`bot/wizard.py`, `_kb_settings_menu`)

```python
[InlineKeyboardButton(
    text="🌐 Платформы: TG · Site · Discord · VK",
    callback_data="gateway:home",
)]
```

- Позиция: рядом с «⛔ Доступ» (это тоже админ-функция).
- Видимость: только владелец/со-владелец (как «⛔ Доступ»). Гости кнопку не видят даже в непривычном режиме — добавить `"gateway:"` в соответствующие карты `feature_gate` либо гейтить по `is_owner_or_co_owner`.

### 4.4. Флоу ввода токена (строго по паттерну Slack-коннектора)

1. Кнопка `[🔌 Подключить]` → FSM-состояние «жду токен», подсказка формата.
2. Пользователь присылает токен сообщением.
3. Бот **немедленно удаляет сообщение** с токеном (`message.delete()`, в try/except — в личке TG удаление доступно).
4. Валидация: Discord — `GET /users/@me` с этим токеном; VK — `groups.getById` + проверка права `messages`.
5. Ошибки переводить на человеческий (словарь в стиле `slack/client.py::_friendly`):
   - Discord `401` → «Токен не принят. Скопируй Bot Token заново: Developer Portal → Bot → Reset Token.»
   - Discord без интента → «Включи MESSAGE CONTENT INTENT: Developer Portal → Bot → Privileged Gateway Intents.»
   - VK `access denied` → «Ключу не хватает права "Сообщения сообщества". Пересоздай ключ с этим правом.»
6. Успех → сохранить в `addon_state`, показать экран платформы со статусом ✅, запустить адаптер фоновой задачей.
7. В любом UI токен показывается ТОЛЬКО маской: `MTA4…k2Xw` (первые 4 + последние 4).

### 4.5. Флоу привязки аккаунта `gateway:link`

```
🔗 Привязка аккаунта

Твой код: 483920
Действует 10 минут.

Напиши этот код боту в Discord или VK —
и та платформа получит права владельца.

[🔁 Новый код]  [📋 Мои привязки]  [↩️ Назад]
```

- Код: 6 цифр, `secrets.randbelow`, TTL 10 минут, одноразовый, максимум 3 активных кода.
- **Хранение кода:** код хранится в `pending_codes` как есть — короткий TTL (10 минут), одноразовость и rate-limit делают это приемлемым. Исполнитель МОЖЕТ (MAY) дополнительно хранить SHA-256-хэш вместо открытого кода со сравнением через `hmac.compare_digest` — это необязательная рекомендация, а не требование; не усложнять реализацию ради неё.
- **Только личные сообщения (MUST):** код принимается ТОЛЬКО в DM (Discord) / личке сообщества (VK). Шестизначное сообщение в публичном канале/беседе игнорируется с подсказкой «напиши код мне в личку» — иначе владелец, случайно отправивший код в общий канал, устраивает гонку «кто первый пришлёт код, тот и владелец».
- На стороне Discord/VK: входящее DM-сообщение, состоящее ровно из 6 цифр, проверяется по `pending_codes`. Совпало → создать запись в `links`, погасить код, ответить «✅ Аккаунт привязан к владельцу» И отправить владельцу в TG уведомление «🔗 К аккаунту привязан Discord-аккаунт <tag> [🗑 Отвязать]» — чтобы перехват кода был немедленно виден и обратим одной кнопкой.
- `[📋 Мои привязки]` → список связок с кнопкой «🗑» у каждой (отвязать = разжаловать в гостя мгновенно).
- Rate limit на переборы: после 5 неверных кодов с одного `external_id` — игнор кодов от него на 1 час + уведомление владельцу в TG.

## 5. Discord-адаптер — детальные требования

- **Библиотека: `discord.py` ≥ 2.x** — выбор подтверждён живыми метриками GitHub (§9А.1: 16 099★, последний push 25.05.2026). Допустимые альтернативы при аргументации в changelog: `nextcord` (drop-in), `interactions.py` (slash-центричный), `hikari` (микрофреймворк).
- Лимиты UI (проверены, §9А.3): ≤5 кнопок в Action Row, ≤40 компонентов на сообщение (Components V2), `custom_id` ≤100 символов, нельзя смешивать кнопки и селект в одном Action Row.
- **Режим: Gateway (WebSocket)** — не требует публичного URL, работает на Render Free. HTTP Interactions Endpoint (с Ed25519-верификацией) — осознанно отложен (записать как future work).
- Интенты: `message_content` (включить в Developer Portal!), `guilds`, `dm_messages`.
- Жизненный цикл: `asyncio.create_task(adapter.start())` из `bot/main.py` рядом с регистрацией аддонов; graceful shutdown при остановке процесса; при `enabled=true` и живом токене — автостарт при каждом рестарте (R9).
- Реконнекты: `discord.py` реконнектится сам; наша обязанность — счётчик ошибок для экрана статуса и лог `logging.getLogger("gateway.discord")` (БЕЗ токена в сообщениях).
- Rate limits: библиотека обрабатывает 429 сама; наши правила — не редактировать одно сообщение чаще 1 р/сек, меню-ответы всегда через interaction response (не отдельными сообщениями).
- Slash-команды: `/menu`, `/settings`, `/status`, `/link <код>` (альтернатива вводу кода простым сообщением). Синхронизация команд — при старте адаптера.
- **Кнопки обязаны переживать рестарт (MUST, research §9Б.1).** Известная боль discord.py: View-кнопки с `timeout` умирают после рестарта бота («This interaction failed»). Наш случай решается элегантнее стандартного `persistent view`: НЕ использовать View-коллбеки для меню вообще. Вместо этого — единый обработчик `on_interaction`, который читает `custom_id` (= наша action-строка, например `roles:menu`) и передаёт его в `dispatch_action`. Тогда кнопки stateless по построению: рестарт процесса не ломает ни одно старое сообщение с меню. Если где-то всё же нужен View — только `timeout=None` + фиксированные `custom_id` + `bot.add_view()` в `setup_hook` (официальный пример `Rapptz/discord.py/examples/views/persistent.py`).
- **Правило 3 секунд (MUST, research §9Б.2).** Discord требует ответ на interaction в течение 3 секунд, иначе «interaction failed». Правило адаптера: если `dispatch_action` может работать дольше (медиаобработка, вызов мозга) — немедленно `await interaction.response.defer()` (окно расширяется до 15 минут), результат отдавать через `edit_original_response`/`followup`. Быстрые экраны меню отвечают сразу через `interaction.response.edit_message`.
- **Экономия RAM (SHOULD, research §9Б.5):** при создании клиента задать `chunk_guilds_at_startup=False` и `member_cache_flags=discord.MemberCacheFlags.none()`, интенты — только необходимый минимум (§5 выше). Боту не нужен кэш участников серверов — он работает с одним владельцем и DM. Это напрямую снижает RSS на Render Free (риск №1 из §12).
- **Запуск в общем loop (MUST, research §9Б.3):** НИКОГДА не вызывать `bot.run()` — он создаёт и захватывает собственный event loop и несовместим с aiogram в одном процессе. Только `await bot.start(token)` внутри `asyncio.create_task(...)` из общего loop, остановка — `await bot.close()`.

В vkbottle это `event.show_snackbar(...)` / `event.edit_message(...)` (высокоуровневый `MessageEvent`-дataclass, см. `vkbottle/examples/high-level/message_event.py`). Правило: сначала ack (snackbar или edit), потом любая долгая работа.
- Жизненный цикл, логирование, автостарт — зеркально Discord (§5), включая запуск через `create_task` в общем loop (§9Б.3).

## 6А. Медиашина: кросс-платформенный медиаконвейер (R11–R12)

### 6А.1. Целевой сценарий владельца (дословный пример, обязан работать)

> Сделал фотку в TG → обработал её функцией бота в Discord (img2img / rmbg) → результат получил обратно в TG → одной кнопкой закинул полученную фотку в генерацию видео (img2video).

Обобщение: **медиафайл, попавший в бота на любой платформе, становится общим «артефактом» и может быть обработан/получен/дообработан с любой другой платформы.** Кнопка «📸 Генерация фото и видео» (`photogen:open`) и флоу «прислал фото → Фото/Видео» из `bot/media_ui.py` должны работать на всех четырёх платформах.

### 6А.2. Принцип: артефакты, а не пересылка файлов

Вводится реестр **медиа-артефактов** в `bot/gateway/media_bus.py`:

```python
@dataclass
class MediaArtifact:
    id: str              # короткий id, например "m7f3" (≤6 симв. — влезает в action-строки, лимит 64 байта!)
    kind: str            # "photo" | "video"
    origin: dict         # платформо-нативный УСТОЙЧИВЫЙ указатель (НЕ прямой URL!), см. §6А.6:
                         #   TG:      {"platform": "telegram", "file_id": "..."}
                         #   Discord: {"platform": "discord", "channel_id": ..., "message_id": ..., "attachment_id": ...}
                         #   VK:      {"platform": "vk", "peer_id": ..., "cmid": ...}  # для messages.getById
                         #   VISION:  {"platform": "web", ...}  # см. открытый вопрос в §6А.6
    created_at: float
    chain: list[str]     # история обработки: ["tg:upload", "discord:img2img", ...]
    parent_id: str | None  # артефакт-родитель (результат img2img помнит исходник)
```

Ключевые решения (исполнитель обязан их соблюдать, отклонения — через changelog):

1. **Байты НЕ храним.** Правило §13.4 («никаких новых файлов на диске») остаётся в силе. В `state.json` (через `addon_state("gateway", "media_artifacts", ...)`) лежат только метаданные + платформо-нативные ссылки: TG `file_id`, Discord attachment URL, VK doc/photo URL. Байты скачиваются лениво в момент обработки — ровно так уже работает `media_ui.py` («Photo bytes are not cached — the file_id … re-downloaded on every leaf action»). Этот паттерн распространяется на все платформы.
2. **Кольцевой буфер:** максимум **10 последних артефактов**, старые вытесняются. Никакого бесконечного роста `state.json`.
3. **Протухание ссылок — решено через устойчивые указатели (research §6А.6):** прямые URL НЕ сохраняются нигде (Discord CDN URL умирают через 24 ч, ссылки из VK Long Poll — ещё быстрее). В `origin` хранится только устойчивый указатель (TG `file_id` / Discord message-координаты / VK message-координаты), а свежий URL добывается резолвером в момент скачивания. Если исходное сообщение удалено — честная ошибка «артефакт истёк, пришли файл заново», НЕ падение.
4. **Обработка — только в ядре.** `bot/media.py` уже принимает байты и не знает про Telegram — «обработать в боте дискорда» означает: Discord-адаптер принял файл → зарегистрировал артефакт → вызвал те же `image_to_video`/img2img-функции `media.py` → результат зарегистрирован новым артефактом с `parent_id`. Дублировать провайдерную логику в адаптерах ЗАПРЕЩЕНО.

### 6А.3. UX

**Вход медиа (любая платформа).** Пользователь прислал фото/видео боту в Discord/VK/TG или загрузил через VISION (новый эндпоинт Fable5 `POST /media/upload`, multipart) → артефакт регистрируется → пользователю показывается стандартный экран выбора «Фото / Видео / Убрать фон» (тот же `MenuScreen`, что и в TG-флоу `photo:*`).

**Экран результата обработки (после любой операции, на любой платформе):**

```
✅ Готово: img2img (мозг: deapi) · артефакт m7f3
[🎬 Сделать видео из этого]   ← одна кнопка = целевой сценарий R12 (action: photo:video:m7f3)
[♻️ Обработать ещё раз]  [🖼 Убрать фон]
[📤 Получить в: TG ✓ · Discord · VK]   ← доставка результата на выбранную платформу
[🗂 Мои медиа]
```

**Экран «🗂 Мои медиа» (`gateway:media`)** — новый пункт в `gateway:home` и в меню «📸 Генерация фото и видео»: список ≤10 артефактов (`kind`, откуда, цепочка обработки, возраст), по клику — тот же экран действий. Это и есть механизм «взять результат в TG»: владелец открывает 🗂 в TG и видит артефакт, созданный из Discord.

**Доставка (`📤`):** отправка артефакта личным сообщением на выбранную платформу возможна только владельцу и только на привязанные платформы (`identity.py`). Гости — гейт через `feature_gate` (право `photogen`).

### 6А.5. Ограничения и честность

- Размер: лимит на скачиваемый файл (по умолчанию 20 МБ — это подтверждённый жёсткий лимит TG Bot API на download; обойти можно только собственным local Bot API server — вне рамок) — больше → честный отказ.
- Видео-артефакты как ВХОД обработки — вне рамок (Non-Goal): вход конвейера — фото; видео появляется только как РЕЗУЛЬТАТ img2video и доставляется по `📤`.
- Одновременная обработка одного артефакта с двух платформ — не блокируем, но результат каждой регистрируется отдельным артефактом (никакой перезаписи).

### 6А.6. Резолверы медиассылок — результаты research (проверено 08.07.2026)

TTL и правильный способ получения байтов для каждой платформы **уже выяснены** — это закрывает бывший research-пункт §9 п.7. Исполнитель реализует резолверы строго по этой таблице:

| Платформа | Что хранить в `origin` | TTL / поведение | Резолвер (как получить байты) |
|---|---|---|---|
| Telegram | `file_id` | `file_id` стабилен долгосрочно; `file_path` из `getFile` гарантирован **≥60 минут**, потом просто перезапросить | `getFile(file_id)` → скачать `api.telegram.org/file/bot<token>/<file_path>`. Никогда не кешировать `file_path` дольше часа |
| Discord | `channel_id` + `message_id` + `attachment_id` | Прямые CDN-URL **истекают через 24 ч** (подписанные параметры `ex`/`is`/`hm`, потом 404) | `channel.fetch_message(message_id)` → свежий подписанный `attachment.url` → `attachment.read()`. Хранить URL — запрещено. (Существует и `POST /attachments/refresh-urls`, но re-fetch сообщения проще и покрыт discord.py) |
| VK | `peer_id` + `cmid` (conversation message id) | Ссылки из событий Bots Long Poll протухают быстро — **сохранять их бессмысленно** | `messages.getById(cmid, extended=1)` → свежий URL из объекта вложения → скачать немедленно |
| VISION (web upload) | ⚠️ единственный случай без «родной» платформы-хранилища | — | Выбранное решение: при загрузке через `POST /media/upload` бот немедленно пересылает файл владельцу в TG служебным сообщением → получает `file_id` → `origin` становится telegram-указателем. Плюсы: ноль нового хранилища, консистентно с §13.4. Альтернатива (отклонена): байты в `state.json` base64 — раздувает файл |

**Паттерн подтверждён индустрией:** мосты matterbridge и mautrix решают ту же задачу так же — либо download+re-upload на целевую платформу в момент доставки (matterbridge), либо «ленивые» указатели с редиректом на исходный CDN без промежуточного хранения (mautrix direct media). Наша схема — второй вариант с ленивым скачиванием, а `📤 Получить в:` — первый (download → re-upload нативным сообщением платформы-получателя).

## 9Б. Best practices из открытых проектов (research 08.07.2026) — закрывают слабые места ТЗ

Каждый пункт — проверенное решение из живых проектов/официальных примеров, а не теория. Исполнитель обязан следовать этим паттернам; отклонение — только через changelog.

### 9Б.1. Кнопки Discord, переживающие рестарт (источник: `Rapptz/discord.py` examples + Stack Overflow)

Самая частая ошибка мультиплатформенных Discord-ботов: кнопки, привязанные к View-объекту в памяти, умирают после рестарта («This interaction failed»). Решение для нашей архитектуры (см. врезку в §5): **stateless-роутинг по `custom_id` через `on_interaction`** — `custom_id` = наша action-строка, обработчик один и живёт вне сообщений. Старые сообщения с меню продолжают работать после любого количества рестартов, `bot.add_view()`-регистрация не нужна вовсе. Это устраняет целый класс багов, который в ТЗ v3.5 не был покрыт.

### 9Б.2. Обязательные ack-правила платформ (источники: Discord Developer Docs, dev.vk.com)

| Платформа | Правило | Последствие нарушения |
|---|---|---|
| Discord | Ответ на interaction ≤ 3 с; долгие операции — `defer()` немедленно, потом followup (окно 15 мин) | «This interaction failed» у владельца при любой операции дольше 3 с (медиа, мозг) |
| VK | Каждое `message_event` — обязательный `messages.sendMessageEventAnswer` (в vkbottle: `event.show_snackbar` / `event.edit_message`) | Вечный спиннер на кнопке |
| Telegram | `answer_callback_query` (aiogram делает это в существующем коде) | Спиннер ~30 с |

Правило адаптеров: **сначала ack, потом работа.** Добавить в тесты §10: мок-операция длительностью 5 с не роняет interaction (Discord-адаптер дефернулся).

### 9Б.3. Три async-клиента в одном процессе (источники: разборы «Run Multiple Asyncio Frameworks», ofeng.org; issue Rapptz/discord.py#516)

Подтверждённый паттерн — **один общий event loop**, каждый клиент — задача:

```python
# bot/main.py — рядом с существующим стартом
tasks = [
    asyncio.create_task(dp.start_polling(bot)),          # aiogram — как сейчас
    asyncio.create_task(discord_adapter.start()),        # внутри: await client.start(token) — НЕ client.run()!
    asyncio.create_task(vk_adapter.start()),             # vkbottle: await bot.run_polling() эквивалент
]
```

Ловушки, подтверждённые сообществом:
- `discord.py client.run()` создаёт СВОЙ loop и блокирует поток — использовать только `await client.start(token)`.
- Graceful shutdown: по SIGTERM — `client.close()` / остановка polling каждого клиента, потом `gather` с таймаутом. Порядок: сначала адаптеры, потом aiogram (TG — последним, чтобы владелец получил уведомление о рестарте, если оно есть).
- Альтернатива «каждый клиент в своём потоке» рассмотрена и отвергнута: усложняет доступ к общему `state.json` и `feature_gate` (пришлось бы городить межпоточную синхронизацию).

### 9Б.4. Supervisor для адаптеров: рестарт с backoff вместо голого `create_task` (паттерн Erlang/OTP, применённый в asyncio-проектах)

Голый `create_task(adapter.start())` — тихая смерть: упавшая задача просто исчезает, владелец видит «не работает» без диагностики. Требование (SHOULD):

- Каждый адаптер оборачивается в supervisor-цикл: упал → лог → рестарт через exponential backoff (1с → 2с → … → cap 60с, с джиттером).
- **Crash-loop-предохранитель:** ≥5 падений за 3 минуты → адаптер выключается (`enabled` не трогаем, но задача не перезапускается до ручного «🔄 Перезапустить»), владельцу — уведомление в TG с последней ошибкой.
- Счётчики падений/рестартов — на экран «📡 Статус» (R10): это и есть его «живая диагностика».

### 9Б.5. Render Free усыпляет процесс — факт, влияющий на ВСЁ (источник: docs.render.com + опыт сообщества)

Render Free web service засыпает после **15 минут без входящего HTTP-трафика**; polling/WebSocket-клиенты (aiogram, discord.py, vkbottle) входящего HTTP НЕ создают. Следствия:

- Это уже сейчас относится к текущему TG-боту (он живёт, только пока его пингуют — heartbeat-механика из §2 п.10, видимо, этим и занимается). Исполнитель на этапе 0 ОБЯЗАН выяснить, чем инстанс удерживается от сна сейчас, и зафиксировать в changelog.
- Все три адаптера обязаны **сами переживать цикл «уснул → проснулся»**: реконнект после resume у discord.py и vkbottle встроен, но supervisor из §9Б.4 — вторая линия обороны.
- Если инстанс всё же засыпает — стандартное решение сообщества: внешний пингер (cron-job.org / UptimeRobot / GitHub Actions) на существующий health-эндпоинт каждые 5–10 минут. Настройка пингера — вне кода, но инструкцию для владельца добавить в `[❓ Как получить токен]`-стиле экран «📡 Статус» (MAY).

### 9Б.6. Атомарная запись `state.json` (источники: safeatomic, разборы crash-safe JSON) — ПОДТВЕРЖДЕНО ПО ЖИВОМУ КОДУ

С приходом трёх адаптеров писать в `state.json` начнут конкурентные задачи одного loop. Стандартный паттерн атомарности: **записать во временный файл рядом → `flush()` + `os.fsync()` → `os.replace()`** (атомарный своп на том же файловом разделе); конкурентность внутри процесса — один `asyncio.Lock` вокруг записи.

**Факт из живого кода (проверено 08.07.2026):** `bot/storage.py::Storage._save()` (строка ~94) пишет голым `self.state_file.write_text(json.dumps(...))` — НЕ атомарно. Креш/OOM-kill посреди записи оставляет обрезанный JSON, а `_load()` при ошибке парсинга молча возвращает `{}` — т.е. повреждение = **тихая полная потеря всех настроек и токенов**. Требование (MUST этапа 0): заменить тело `_save()` на temp+fsync+`os.replace` и обернуть в `asyncio.Lock`, НЕ меняя сигнатуру и вызовы; в `_load()` при битом JSON — НЕ возвращать `{}` молча, а попытаться загрузить бэкап (см. §9Б.7) и громко залогировать.

### 9Б.7. Эфемерный диск Render Free — где на самом деле живёт `state.json` (источник: docs.render.com; проверено по `bot/config.py`)

Факты: (а) на Render Free файловая система **эфемерная** — всё содержимое диска теряется при каждом деплое, рестарте и усыплении; (б) persistent-диски на Free-тарифе **недоступны**; (в) живой код (`bot/config.py::_default_data_dir`) предпочитает `/data` (persistent-диск из Blueprint) с фолбэком в эфемерный путь. Следствия:

- Исполнитель на этапе 0 ОБЯЗАН (MUST) выяснить фактическую конфигурацию: какой тариф у сервиса и примонтирован ли `/data`. Если диска нет — токены Discord/VK, привязки и настройки будут теряться при каждом рестарте, и вся работа этапов 1–3 бессмысленна до решения этой проблемы. Результат проверки — в changelog, блокер этапа 0 наравне с замером RAM.
- Страховка независимо от тарифа (SHOULD): кнопка «💾 Экспорт настроек» на экране «📡 Статус» — бот присылает владельцу в TG файл `state.json` (это DM владельца — приемлемо, токены и так его); зеркальная «📥 Импорт» — принять файл документом. Это бэкап «в один тап» без внешних сервисов, паттерн многих селф-хостед ботов.
- Автобэкап (MAY): раз в сутки слать `state.json` владельцу в TG тихим сообщением — дешёвая защита от внезапной потери диска.

### 9Б.8. Двойной запуск при деплое: TG 409 Conflict (источники: core.telegram.org, разборы Telegraf/aiogram)

Telegram допускает **один** активный `getUpdates` на токен. При деплое на Render новый инстанс стартует, пока старый ещё жив (плюс сессия на стороне TG держится до ~30 с после остановки) → новый инстанс ловит `409 Conflict`. То же по смыслу касается Discord (лимит сессий Gateway) и VK Long Poll. Требования:

- Polling-циклы всех трёх клиентов при 409/конфликте сессии — retry с backoff (supervisor §9Б.4 покрывает это автоматически), НЕ падать и НЕ считать это фатальной ошибкой первые ~60 с после старта.
- Graceful shutdown по SIGTERM (MUST): остановить polling всех клиентов и закрыть сессии ДО выхода процесса — освобождает `getUpdates` для нового инстанса и сокращает окно конфликта.

### 9Б.9. `schema_version` в `state.json` (источник: паттерн «versioned config», GitHub-проекты versionable / version-migrate)

ТЗ добавляет в `state.json` новые ветки (`gateway` §3.5). Чтобы будущие изменения структуры не ломали старые файлы молча, требование (SHOULD, дёшево):

- В корень ветки `gateway` добавить поле `"schema_version": 1`.
- При загрузке: версия меньше текущей → прогнать список миграций (обычные функции `dict → dict`, по одной на версию); версия больше текущей (откатили код) → не трогать ветку и громко залогировать.
- Это ~20 строк кода, но устраняет целый класс «тихих» багов при эволюции схемы — тот же принцип, что миграции БД.

### 9Б.10. Логи адаптеров с полем платформы (источник: практики structured logging для мультиплатформенных ботов)

Когда платформ три, лог «кнопка не сработала» без указания откуда — бесполезен. Требование (SHOULD): каждая запись лога из адаптеров и `dispatch_action` содержит префикс/поле платформы (`[tg]` / `[discord]` / `[vk]`) и `user_ref` (§3.4). Формат — как принято в текущем коде (обычные строки с префиксом достаточны, structured JSON не обязателен). Последние N ошибок каждого адаптера хранить в кольцевом буфере в памяти — их показывает экран «📡 Статус» (R10), это его «последняя ошибка» без чтения логов Render.

### 9А.4. Best practices привязки аккаунтов (интернет-research)

Наш флоу §4.5 (одноразовый код) подтверждён как индустриальный паттерн; research добавил уточнения:

1. **Таблица связок** `links` (platform + external_id → user_id) — ровно то, что заложено в §3.5. Валидация кода — строго на стороне бота, до записи в `links`.
2. **Обратное направление привязки** (из Discord/VK → в TG) — использовать deep-link `https://t.me/<bot>?start=<одноразовый-токен>`: пользователь кликает, бот в TG валидирует токен и создаёт связку. Добавить как альтернативный флоу `[🔗 Привязать через Telegram]` на этапе 2 (SHOULD, не MUST).
3. **Discord OAuth2 (PKCE)** — «правильный» способ верификации Discord-личности для веба, но требует публичного redirect URI и регистрации в Developer Portal. Для нашего бота избыточен — код-флоу достаточен. Зафиксировано как future work для VISION («Войти через Discord»).
4. Одноразовость, TTL и rate-limit (уже в §4.5) — обязательные элементы паттерна, подтверждено.

| Медиассылки протухают (Discord CDN 24 ч, VK Long Poll — сразу) | высокая | низкий (снят) | Решено архитектурно (§6А.6): в `origin` только устойчивые указатели, свежий URL — через резолвер (`getFile` / `fetch_message` / `messages.getById`) в момент скачивания; при удалённом исходном сообщении — честная ошибка «артефакт истёк» |
| Большие файлы забьют RAM при скачивании | средняя | средний | Жёсткий лимит 20 МБ (§6А.5), скачивание стримом с обрывом по превышению |
| Токены открытым текстом в `state.json` утекают через бэкап/дамп файла | низкая | высокий | Осознанный компромисс (консистентно с ключами мозгов, §9 п.6): бэкапы `state.json` не публикуются; «🗑 Отключить» стирает токен, а после подозрения на утечку владелец обязан пересоздать токен на стороне платформы (Reset Token / пересоздать ключ сообщества). Обфускация при хранении (XOR/base64) — MAY, шифрование с ключом — избыточно (ключ негде хранить: env vars запрещены §13.2) |

### 12.1. Модель угроз (STRIDE-lite для внешних платформ)

Внешние платформы = новая поверхность атаки. Каждая угроза покрыта конкретным контролем в дизайне:

| Угроза (категория STRIDE) | Вектор | Контроль в ТЗ |
|---|---|---|
| Spoofing — самозванец получает права владельца | Перебор кодов привязки ботом-переборщиком | 6 цифр × TTL 10 мин × ≤3 активных кода × блок после 5 ошибок на 1 час (§4.5) — перебор статистически бессмыслен |
| Spoofing — перехват кода | Владелец случайно отправил код в публичный канал | Код принимается только в DM; уведомление владельцу в TG с кнопкой «🗑 Отвязать» при каждой новой привязке (§4.5) |
| Tampering — подмена action-строк | Гость шлёт произвольный `custom_id`/`payload` с чужим действием | Каждое действие проходит `feature_gate` в `dispatch_action` (§3.4) — источник callback-строки не доверенный по определению |
| Information Disclosure — утечка токена | Логи, трейсбеки, экраны статуса | Токен нигде не выводится, кроме маски `xxxx…xxxx` (§4.4 п.7, R7-E1); grep-проверка логов — обязательный пункт DoD (§8.2) |
| Information Disclosure — код привязки в хранилище | Дамп `state.json` раскрывает активные коды | TTL 10 минут + одноразовость + приём только в DM резко сужают окно атаки (§4.5); хэш-хранение — необязательная опция (MAY) |
| Denial of Service — флуд гостей на внешней платформе | Спам кнопками/сообщениями в Discord/VK | Rate limit на interaction per-user (переиспользовать паттерн rate-limit привязки); лимит «не чаще 1 edit/сек» (§5); процесс не падает при недоступности платформы (§10.1) |
| Elevation of Privilege — гость видит админ-экраны | Прямой вызов `gateway:*`-действий без кнопки | Гейт по `is_owner_or_co_owner` на уровне диспетчера, не рендера (§4.1): скрытая кнопка ≠ защита, проверка на каждом действии |

## 13. Правила и ограничения (нарушение = возврат на доработку)

1. **TG — священен.** Любое видимое изменение существующего TG-поведения без явного требования этого ТЗ — блокер.
2. **Ноль новых обязательных env vars.** Всё подключается кнопками (философия проекта: «один секрет BOT_TOKEN, остальное изнутри»).
3. **Опциональные зависимости.** `discord.py`, `vkbottle` — extras; их отсутствие не мешает старту (мягкий try/except как в `build_addon_routers`).
4. **Состояние — только через `bot/addons/state.py`.** Никаких новых файлов на диске.
5. **Не дублировать логику.** Гейтинг — только `feature_gate`; VISION-флоу — существующие обработчики; валидация ошибок — по образцу `slack/client.py`.
6. **Конвенции проекта.** Стиль, структура аддонов, логгеры `logging.getLogger("gateway.<...>")`, docstrings в стиле существующих модулей.
7. **Changelog.** После каждого этапа — запись в `AI_CHANGELOG.md` (формат из `AGENTS.md`): что сделано, что выбрал, почему, что отложено.

## 15. FAQ исполнителя

**Почему не три отдельных бота?** Потому что тогда каждая новая кнопка требует трёх правок и неизбежно расползается. Требование владельца R5 выполнимо только через единый источник меню.

**Можно взять готовый мультиплатформенный фреймворк?** Нет (Non-Goals). Проект — набор лёгких аддонов на одном asyncio-loop; тяжёлый фреймворк сломает философию и память Render Free. Идеи — да, зависимости — нет.

**Что делать с экранами, которые физически невозможны вне TG (например, требуют TG-специфичных сущностей)?** Заглушка `tg_only` с deep-link — это законный постоянный ответ, а не временный костыль. Отметить такие экраны списком в changelog.

**Куда писать вопросы по неоднозначностям?** Сначала — поиск ответа в коде и `AGENTS.md`; если неоднозначность осталась — зафиксировать принятое решение и аргументы в `AI_CHANGELOG.md`, выбрав вариант, минимально трогающий TG.

## 15А. Реестр архитектурных решений (ADR)

Ключевые решения зафиксированы в формате ADR (Architecture Decision Record). Пересмотр любого ADR — только с новой записью здесь и в `AI_CHANGELOG.md`; молча отклоняться от принятого ADR запрещено.

### ADR-001: Один бот с адаптерами вместо трёх отдельных ботов
- **Статус:** принято
- **Контекст:** владельцу нужно «добавил кнопку — видна везде» (R5); три бота = тройная стоимость каждой правки и неизбежный дрейф меню.
- **Решение:** единый `MenuScreen` + тонкие адаптеры per-платформа (§3.1).
- **Последствия:** ➕ R5 выполняется автоматически; ➕ одна кодовая база. ➖ адаптеры обязаны честно транслировать лимиты платформ (пагинация VK, селекты Discord).

### ADR-002: Токены в `state.json` через кнопки, а не env vars
- **Статус:** принято
- **Контекст:** философия проекта «один секрет BOT_TOKEN, остальное изнутри»; Render Free бэкапит один файл.
- **Решение:** флоу Slack-коннектора (FSM → валидация → удаление сообщения → `addon_state`), ноль новых обязательных env vars (§4.4, §13.2).
- **Последствия:** ➕ подключение платформ без доступа к хостингу; ➖ токены в открытом виде в `state.json` — риск принят и митигирован (§12, последняя строка).

### ADR-003: Медиашина на артефактах-указателях, а не на копировании файлов
- **Статус:** принято
- **Контекст:** прямые CDN-ссылки протухают (Discord — 24 ч, VK Long Poll — сразу); хранить байты негде (Render Free).
- **Решение:** `MediaArtifact.origin` хранит устойчивые указатели (file_id / message-координаты), байты резолвятся в момент обработки (§6А.2, §6А.6).
- **Последствия:** ➕ ноль дискового хранилища, риск протухания снят; ➖ при удалении исходного сообщения артефакт честно «истекает».

### ADR-004: `discord.py` и `vkbottle` как опциональные extras, без мультиплатформенного фреймворка
- **Статус:** принято
- **Контекст:** готовые фреймворки (Botpress/Rasa/аналоги, §9А.2) тяжелы для Render Free и ломают философию лёгких аддонов на одном asyncio-loop.
- **Решение:** две зрелые библиотеки (метрики в §9А.1) за общим `base.py`-контрактом; отсутствие библиотек не мешает старту (§13.3).
- **Последствия:** ➕ бот живёт в чистом TG-режиме (A10); ➕ замена библиотеки не трогает ядро; ➖ адаптеры пишем сами.

### ADR-005: Заглушка `tg_only` — законный постоянный ответ для TG-специфичных экранов
- **Статус:** принято
- **Контекст:** часть экранов `wizard.py` физически требует TG-сущностей; полное покрытие всех ~9 500 строк — нереалистично и не нужно.
- **Решение:** волновая миграция экранов (§7); непокрытые/непереносимые экраны отвечают «⏳ доступно только в Telegram» + deep-link.
- **Последствия:** ➕ честный UX вместо сломанных экранов; ➖ список `tg_only`-экранов обязан вестись в changelog.
