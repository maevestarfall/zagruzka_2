## БЛОК 1 — MUST (нарушения обязательных требований ТЗ)

### 1.1. Нет FSM-ввода токена в Telegram (ТЗ §4.4, R6)

**Где:** `bot/gateway/wizard_ui.py` + экраны
`gateway:discord:live` / `gateway:vk:live`.

**Сейчас:** токен Discord/VK можно ввести только с сайта (форма во
вкладке VISION «Меню бота»). В Telegram кнопка «Подключить» лишь
открывает панель, но принять токен сообщением бот не умеет.

**Надо по ТЗ:**
1. Кнопка «Подключить (ввести Bot Token)» в TG переводит владельца в
   состояние «жду токен» (aiogram FSM).
2. Владелец присылает токен обычным сообщением.
3. Бот НЕМЕДЛЕННО удаляет сообщение с токеном из чата
   (`message.delete()`), даже если валидация не прошла.
4. Валидация (см. п. 1.2), сохранение, ответ статусом.
5. Кнопка «Отмена» выходит из состояния.
6. FSM доступен только владельцу/со-владельцу (`access.can_admin`).

### 1.2. Discord-токен сохраняется без валидации (ТЗ §4.4 п.4, §5)

**Где:** `bot/gateway/adapters/discord_gw.py`, обработчик
`gateway:discord:settoken:`.

**Сейчас:** токен пишется в state сразу, без какой-либо проверки.
Ошибка всплывает только после нажатия «Запустить».

**Надо по ТЗ:**
1. Перед сохранением — проверить токен запросом
   `GET https://discord.com/api/v10/users/@me`
   с заголовком `Authorization: Bot <token>` (aiohttp, таймаут 10с).
2. 401 → НЕ сохранять, ответить: «Токен не принят Discord. Проверь,
   что скопировал Bot Token (не Client Secret).»
3. 200 → сохранить + записать `bot_tag` (username#discriminator) из
   ответа, показывать его на экране статуса.
4. Отдельно: если бот стартовал, но падает `PrivilegedIntentsRequired`
   → статус error с текстом «Включи MESSAGE CONTENT INTENT в Discord
   Developer Portal → Bot → Privileged Gateway Intents».

Для сравнения: VK-адаптер уже валидирует через `groups.getById` —
сделать симметрично.

### 1.3. Нет уведомлений владельцу в TG о событиях безопасности (ТЗ §4.5)

**Где:** `bot/gateway/identity.py` (+ нужен доступ к aiogram Bot —
использовать тот же ленивый паттерн, что `bot_username` в addon-state).

**Сейчас:** привязка чужого аккаунта и бан за перебор кодов происходят
молча. Владелец не знает, что к боту привязался Discord/VK-аккаунт.

**Надо по ТЗ:**
1. При успешной привязке (`verify_code` → ok) — отправить владельцу
   в TG: «К аккаунту привязан Discord-аккаунт <label> (id <external_id>)»
   + inline-кнопка «Отвязать» (`gateway:unlink:<platform>:<external_id>`).
2. При бане за перебор (5 неверных кодов) — уведомить владельца:
   «Попытка перебора кодов привязки с <platform> id <external_id>.
   Аккаунт заблокирован на 1 час.»
3. Отправка не должна ломать сам flow привязки (try/except, лог).

### 1.4. VK: усечение клавиатуры вместо пагинации (ТЗ §6)

**Где:** `bot/gateway/adapters/vk_gw.py`, рендер клавиатуры
(сейчас `rows[:6]` + флаг `truncated`).

**Сейчас:** если экран длиннее 6 рядов — лишние кнопки просто
пропадают. Пользователь VK не может добраться до части меню.

**Надо по ТЗ:**
1. Автоматическая пагинация: 5 рядов контента + 1 служебный ряд
   «⬅️ Назад | стр. N/M | ➡️ Вперёд».
2. Callback-действия пагинации — служебные, вида
   `gateway:page:<screen_id>:<n>` (укладываться в 64 байта; для
   длинных screen_id держать номер страницы в state по peer_id).
3. Текущая страница хранится per-peer (addon-state `gateway`,
   ключ `vk_page:<peer_id>`), сбрасывается при переходе на другой экран.

### 1.5. Волна 2 сделана не по ТЗ (ТЗ §7, этап 4)

**Где:** `bot/gateway/screens_wave2.py`.

**Сейчас:** реализованы экраны tokens, debates, promptbox, github,
projmap, misc — это состав ВОЛНЫ 3 по ТЗ.

**Надо по ТЗ (волна 2 — самые частые экраны):**
- роли (`roles:*`)
- память (экран памяти)
- доступ (`access:menu` — только владелец)
- терминал (`term:*` — только владелец)
- мозги/ключи (`brains:*` / ключи — только владелец)
- Slack (`slack:*` — статус/подключение)

Существующие экраны волны 3 НЕ удалять — они уже работают и
покрыты тестами. Нужно ДОБАВИТЬ недостающие экраны волны 2 в тот же
модуль (или `screens_wave2b.py`), по тому же паттерну: builder читает
реальные данные из storage/handlers, mutating-действия регистрируются
через `register_action`, гейтинг внутри builder через
`access.can_admin`.

## БЛОК 2 — SHOULD (отклонения, требующие фикса или аргументации)

### 2.1. Discord: текстовые команды вместо slash-команд (ТЗ §5)

ТЗ описывает `/menu`, `/settings`, `/status`, `/link` как slash-команды
(`app_commands`, `tree.sync()`). Сейчас — текстовые `!lilush ...` +
`/link`-подобный разбор сообщений. Либо мигрировать на slash-команды,
либо записать аргументированное отклонение в `AI_CHANGELOG.md`
(например: «tree.sync() имеет жёсткий rate limit; текстовые команды
проще для self-hosted»). Требование MESSAGE CONTENT INTENT при
текстовых командах — обязательно упомянуть в подсказке владельцу.

### 2.2. Discord: нет defer() для долгих действий (ТЗ §5 MUST при slash)

Если останутся текстовые команды — пункт неактуален (записать это).
Если будут slash-команды: любое действие дольше ~2с обязано сначала
`interaction.response.defer()`, иначе interaction умирает.

### 2.3. Discord: RAM-флаги клиента (ТЗ §9Б.2, §9Б.5)

При создании discord-клиента выставить:
- `chunk_guilds_at_startup=False`
- `member_cache_flags=discord.MemberCacheFlags.none()`
- минимальные intents (только guilds, guild_messages, message_content
  при текстовых командах).
Это прямое требование ТЗ из-за ограничения RAM 512 МБ.

### 2.4. «Чат с мозгом» из Discord/VK (ТЗ R3)

Свободный текст (не команда и не код привязки) от ПРИВЯЗАННОГО
пользователя должен уходить в тот же пайплайн диалога, что и
сообщение в TG (мозг/LLM), с ответом обратно в Discord/VK.
Непривязанный пользователь получает подсказку про привязку.
Если откладывается на этап 5 (медиашина) — записать это решение
в `AI_CHANGELOG.md`.
